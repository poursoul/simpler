# 多核共享任务认领的同地址返回型 atomic 竞争问题

## 1. 文档定位

本文只定义一个通用问题：多个 scalar worker 同时竞争同一个任务时，如何在
保持业务语义不变的前提下，降低 A5 上共享热点 atomic 的性能代价。

本文是一份**问题与约束说明**，不是当前源码导读，也不是方案设计稿。读者
无需了解 standalone 调度器、TensorMap 或 PA 的实现即可理解本文。本文不预设
必须继续使用 `FetchMax`，也不推荐 CAS、Exchange、分层竞争或任何其他替代
协议。

文中的当前实测证据冻结在以下条件：

- 日期：2026-07-31；
- 代码基线：`e276a9c1d8bb66b287de08975caf922b397ece1c`；
- 设备：A5；
- 负载：B256，共 `256 × 5 = 1,280` 个逻辑任务；
- 三类任务的合法候选数固定为 `24 / 32 / 64`；
- CPU 仅用于协议正确性验证，不能替代 A5 性能数据。

## 2. 不依赖实现的问题模型

对任意逻辑任务 `T`，调度器给出一个合法候选集合 `E(T)`，其大小为 `N`。
这些 worker 可能近似同时到达任务认领点：

```text
N 个合法候选 worker
        │
        ▼
  任务 T 的认领协议
        │
        ├── 恰好 1 个 winner：负责后续 winner-only 工作
        └── N - 1 个 loser：确认失败后尽快离开
```

认领协议必须同时回答两件事：

1. 当前 worker 是否获得任务 `T`；
2. 所有合法候选完成竞争后，任务 `T` 是否恰好产生一个 winner。

当前实现以单调共享状态完成认领，其核心语义可抽象为：

```text
old = atomic_max(shared_state, task_id)
won = old < task_id
```

这里的 `atomic_max` 只是当前证据来源，不是未来实现必须保留的接口。问题的
本质是：同一任务的多个候选访问同一个共享仲裁状态，而且每个调用者必须根据
atomic 返回值判断 winner 或 loser。

## 3. 为什么“消费 atomic 返回值”是关键约束

atomic 观察必须区分两种边界：

- `source_issue`：只说明源码已经发射 atomic，不能说明结果已经返回；
- `return_ready`：后续控制流真实消费 atomic 返回值，必须等到该值可用。

任务认领属于第二种。loser 不能在发射 atomic 后立即离开，因为它必须先知道
自己确实没有获胜；winner 同样要等返回值才能进入 winner-only 路径。

华为官方接口说明中，`AtomicMax` 返回目标 GM 地址执行原子操作前的旧值：

- [Ascend C AtomicMax 官方说明](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_00261.html)

因此，当前泳道中的 `claim_max` 表示带返回依赖的观测区间，而不是只包围指令
发射的极短区间。它仍不代表全系统可见性屏障，也不能被解释成 atomic 硬件
单元的纯指令延迟。

## 4. 当前业务规模与竞争人口

当前 B256 负载包含五类任务。为了把业务名称与通用问题分开，可将它们归纳成
三种竞争人口：

| 业务实例 | 每任务合法候选数 `N` | 当前候选角色 |
| -------- | -------------------: | ------------ |
| Alloc | 24 | 8 个 AIC + 16 个 AIV |
| QK / PV | 32 | AIC |
| SF / UP | 64 | AIV |

在 256 个 batch group 中，每组各有一个 Alloc、QK、SF、PV 和 UP，因此：

| 任务类别 | 逻辑认领次数 | winner | true loser |
| -------- | -----------: | -----: | ---------: |
| Alloc | 6,144 | 256 | 5,888 |
| QK + PV | 16,384 | 512 | 15,872 |
| SF + UP | 32,768 | 512 | 32,256 |
| 合计 | 55,296 | 1,280 | 54,016 |

在当前业务合同下，`55,296` 次逻辑认领中有 `54,016` 次最终为 loser，true
loser 比例为：

```text
54,016 / 55,296 = 97.685%
```

这意味着认领路径的单位成本会被大量 loser 放大。优化对象不是少数 winner
的单次延迟，而是固定候选人口下所有 winner 与 loser 共同承担的仲裁成本。

## 5. A5 当前性能事实

### 5.1 完整泳道样本

当前正式的 A5、B256、`24/32/64` 样本为：

```text
tests/atomic_probe/pa_scheduler/test_record/2026-7-31/
  shared_b256_g1_alloc24_cube32_vector64_1817290us_merged_swimlane.json
```

该诊断构建的完整 Submit wall time 为 `1,817.290 us`。逐 atomic 统计如下：

| 观测点 | 次数 | 累计 core-time | mean | median | p95 | max |
| ------ | ---: | -------------: | ---: | -----: | --: | --: |
| `claim_max` | 55,296 | 46.041 ms | 832.6 ns | 517 ns | 2,749 ns | 14,384 ns |
| `fanin_flag_load` | 44,700 | 11.407 ms | 255.2 ns | 257 ns | 369 ns | 742 ns |

这里必须遵守以下解释：

- `累计 core-time` 是所有核、所有调用区间的时长之和；
- 多核调用大量重叠，所以 `46.041 ms` 不能加到或减出 `1.817 ms` 的 Submit
  wall time；
- 表中区间包含必要的返回依赖以及观测边界开销，不是裸 atomic 指令延迟；
- `fanin_flag_load` 访问分散的 producer flag，不能根据全局调用数推断其同址
  并发宽度。

### 5.2 同址候选人口与观测延迟

同一份泳道按任务类别拆分后的 `claim_max` 数据为：

| 任务类别 | 每任务候选数 | mean | median | max | 累计 core-time |
| -------- | -----------: | ---: | -----: | --: | -------------: |
| Alloc | 24 | 283.0 ns | 275 ns | 955 ns | 1.739 ms |
| QK | 32 | 556.9 ns | 465 ns | 3,399 ns | 4.562 ms |
| PV | 32 | 533.8 ns | 445 ns | 3,598 ns | 4.373 ms |
| SF | 64 | 1,085.7 ns | 682 ns | 14,384 ns | 17.788 ms |
| UP | 64 | 1,073.0 ns | 678 ns | 13,373 ns | 17.579 ms |

该结果证明了当前负载中的相关性：同一共享状态的候选人口从 24 增至 32、64
时，返回就绪区间及其长尾显著增加。从软件可见效果看，请求会在热点状态上
产生明显排队；本文不据此臆测 A5 内部具体在哪一级缓存、互连或 atomic 单元
完成串行化。

`fanin_flag_load` 的 AIC/AIV mean 分别约为 `256.6 ns` 和 `254.5 ns`。它有
真实开销，但当前样本没有出现 `claim_max` 随竞争人口增大而产生的同等级长尾，
因此两者不能被混为同一种性能问题。

### 5.3 无泳道端到端基线

当前 `24/32/64` 的 B256 perf-clock 10 次结果为：

| 指标 | Submit 时间 |
| ---- | ----------: |
| mean | 1,762.728 us |
| median | 1,757.651 us |

历史 `96/32/64` 基线的 mean / median 分别为 `2,305.596 / 2,304.520 us`。
将 Alloc 合法候选从 96 改为 24 后，median 改善 `23.730%`。该对照只能用于
确认认领成本对同址竞争人口高度敏感，不能作为继续缩小候选人口的授权；本轮
业务约束已经固定为 `24/32/64`。

perf-clock 与完整泳道来自不同诊断强度的 ELF。两者绝对时间不能互相相减，
也不能用其差值估算 atomic 的净成本。perf-clock 负责判断端到端收益，泳道
只负责解释调用次数、返回区间及成本迁移。

## 6. 已确认的 A5 atomic 与缓存约束

以下内容是后续任何实现都必须考虑的已验证边界，不代表推荐某种方案。

### 6.1 返回型读取不是普通读取

当前设备侧 `atomicAdd(address, 0)` 仍是返回型原子读改写，不是免费、无竞争
的普通共享读取。既有 B256 对照在 `FetchMax` 前增加该读取后，perf-clock
median 回退 `2.916%`。因此不能把 add-zero 读取的调用数当作零成本，也不能
仅按“没有改变数值”把它视为普通 load。

另一方面，普通 scalar GM load 经过每核 DCache，当前没有证据表明它可以在
缺少明确发布协议时替代 atomic observation。性能较短不等于具备所需的跨核
一致性语义。

### 6.2 atomic 状态与普通脏数据不能随意共用 cache line

`tests/atomic_probe/ATOMIC_USAGE_GUIDE.md` 中的 A5 定向测试已经证明：

1. 一个 `TaskCell` cache line 先被普通写形成旧的 dirty 快照；
2. 同一 line 内的控制字随后由 atomic CAS 发布新值；
3. 远端 AIV 已经能够读取该 atomic 新值；
4. 原写核再对整条 line 执行 `DCCI CACHELINE_OUT + DSB`；
5. 100/100 轮中，新 atomic 值都被旧 dirty 快照覆盖。

因此，atomic 仲裁状态默认必须位于 atomic-only cache line，不能与后续可能
由普通 store 写入并执行 DCCI 的 payload 共线。对 atomic-only line 也不应
增加没有业务必要的 DCCI。

### 6.3 DSB、DCCI 与 atomic 不能互相替代

- DSB 约束发起核上的顺序和完成边界，不负责选举唯一 winner；
- DCCI 管理本核 DCache entry，不提供 atomic RMW 语义；
- atomic 控制字的更新不自动发布同一对象内的普通 payload；
- ordinary payload 的跨核发布仍需独立、明确的所有权与 DCCI/DSB 协议。

为了让观测时间更“完整”而在被测 Claim 热路径中额外插入 DSB，会改变实际
执行路径，不是可接受的性能测量方法。

### 6.4 尚不能当作事实的内容

当前证据不足以给出以下通用结论：

- 同一 64 B cache line 内不同 atomic word 是否必然彼此串行；
- 不同 64 B cache line 是否一定完全独立；
- CAS、Exchange、FetchAdd 或 FetchMax 在相同竞争拓扑下谁必然更快；
- 某个 atomic 在不消费返回值时，其全局完成时间是多少；
- A5 的软件可见排队具体发生在缓存、互连还是 atomic 执行单元。

这些未知项不能被写成方案依据，除非有同一设备、同一竞争人口和同一返回依赖
条件下的专项实测。

## 7. 任何替代实现必须保持的业务合同

后续实现可以保留、拆分或完全移除当前 `FetchMax`，但必须同时满足以下条件。

### 7.1 候选人口不变

- Alloc 每任务仍有 24 个合法候选；
- QK / PV 每任务仍有 32 个合法候选；
- SF / UP 每任务仍有 64 个合法候选；
- 不允许通过静态 owner、预筛核或增加 `not_attempted` 来隐藏竞争成本；
- 任意合法候选仍有成为 winner 的可能，不得静默改变任务的核角色约束。

### 7.2 恰好一次执行

对每个任务 `T`：

```text
winner_count(T) == 1
```

同时必须保证：

- winner 属于 `E(T)`；
- 不漏 Build、不重复 Build；
- 不漏执行、不重复执行；
- loser 不进入 winner-only 的 Materialize、Register、Build 或执行路径；
- 后继任务的超前到达不能让前序任务永久失去 winner。

“至多一个 winner”不足以证明正确，必须同时证明“至少一个 winner”。

### 7.3 进度与乱序到达

协议必须覆盖真实多核调度中的以下情况：

- winner 在仲裁中途被长时间延迟；
- loser 很快离开并到达后继任务；
- 后继任务先于部分前序候选到达；
- 旧任务被 replay；
- worker 到达顺序和速度在不同运行中变化。

在合法调度和有限设备进展条件下，任何任务都不能永久等待，也不能因为更高
task id 已经出现而被错误跳过。

### 7.4 调度器终态不变

替代协议不得改变任务图和依赖语义，并必须保持以下外部结果一致：

- fanin 与依赖解除关系；
- TensorMap / shared-output 的最终内容；
- heap 申请、释放和回收边界；
- completion 与 drain 终态；
- kernel 参数、真实计算结果及输出 TensorDesc；
- 每类任务的执行核角色约束。

## 8. 性能验证合同

### 8.1 逻辑人口与物理 atomic 必须分开统计

固定业务下，B256 仍应有：

```text
55,296 次逻辑认领参与
1,280 个 winner
54,016 个 true loser
```

替代协议可以改变物理 atomic 的种类、地址和次数，因此不能要求物理 atomic
总数仍等于 `55,296`。报告必须同时给出逻辑认领人口和各类物理 atomic 次数，
防止通过漏记候选或迁移操作制造虚假收益。

### 8.2 三类证据不能混算

| 证据 | 回答的问题 | 不能用于 |
| ---- | ---------- | -------- |
| CPU 确定性交错 | 协议是否会漏 winner、重复 winner、死锁 | 推断 A5 atomic 性能 |
| A5 perf-clock | 端到端性能是否真实改善 | 解释具体 atomic 成本落点 |
| A5 atomic 泳道 | 调用数、返回区间、长尾和成本迁移 | 替代无观察构建的权威基线 |

不同 ELF 的绝对时间不能直接相减。任何性能结论都必须在相同 CANN、相同构建
类型、相同真实计算负载和相同 `24/32/64` 候选人口下进行成对多轮比较。

### 8.3 保留或撤销的最低判据

一个候选实现只有同时满足以下条件，才能被认为解决了本文问题：

1. CPU 确定性交错与完整任务图正确性闭合；
2. A5 B256 每任务恰好一个 winner，逻辑候选人口和业务终态不变；
3. A5 perf-clock 在成对多轮测试中取得稳定端到端改善；
4. atomic 泳道能够说明收益来自热点竞争减轻，而不是漏执行、漏候选或观测缺失；
5. 没有用额外全局屏障、重型 DSB 或新的共享热点掩盖原问题；
6. 没有破坏 atomic-only cache line 与普通 DCCI payload 的隔离约束。

## 9. 明确排除的推断

本文不支持以下结论：

- CPU 上更快的 atomic 协议在 A5 上也会更快；
- 只要单条 atomic 的 mean 下降，Submit 就一定改善；
- 只要 physical atomic 总数下降，同地址长尾就一定下降；
- 只证明没有重复 winner，就已经证明协议正确；
- 继续减少 `24/32/64` 候选人口属于本轮可接受优化；
- 将热点拆成多个地址后一定不存在 cache-line 或互连层面的竞争；
- 某一种分组、层级或 atomic opcode 已经被本文选定为目标方案。

## 10. 最简问题陈述

当前 B256 中，`55,296` 次逻辑认领需要产生 `1,280` 个且仅有 `1,280` 个
winner。`97.685%` 的参与者最终为 loser，但仍必须等待返回型认领结果。
A5 实测显示，当同一任务的共享仲裁状态由 24、32、64 个候选访问时，返回
就绪区间和长尾随竞争人口显著放大，64 路任务的单次观测 max 已达到约
`14 us`。

后续工作的目标是：在候选人口、恰好一次执行、任务依赖、进度和最终计算结果
全部不变的条件下，降低 A5 上这种同地址返回型 atomic 竞争对端到端 Submit
性能的影响。实现可以不再使用 `FetchMax`，但不能通过减少候选、漏掉 loser、
改变 winner 资格或弱化正确性合同来取得收益。
